# 流程、岗位与交付关系

小团队可以兼任岗位，但规则确认、实现和验收应分开检查；不能只凭开发者自测宣布最终验收。

|阶段|负责岗位|输入依据|输出文档|进入下一阶段的条件|
|---|---|---|---|---|
|立项与范围|产品负责人、制作人、技术负责人|目标用户、参考作品、预算和平台限制|项目章程、范围边界、里程碑、风险表|明确做原创类似玩法还是复现指定版本|
|参考研究|游戏策划、规则分析、资料研究|规则书、实物组件、可访问参考站|版本清单、来源台账、观察记录、差异与待确认决策|每条关键规则可追溯，推断与观察分开|
|需求与游戏设计|产品经理、游戏策划、数值策划|研究结论、用户场景|PRD、游戏设计文档 GDD、规则决策表、卡牌与职业数据字典|定义可执行的行为及通过条件|
|体验与视觉设计|UX、UI、美术／动效设计师|PRD、规则状态、素材约束|页面清单、流程图、线框、视觉规范、状态与控件规格、素材清单|所有关键状态和异常路径有设计依据|
|技术设计|架构／技术负责人、前后端、QA、运维|需求、设计、规模目标|架构设计、数据模型、API／消息契约、存档版本方案、测试计划、部署方案|职责、边界、错误和恢复策略明确|
|开发准备|技术负责人、前后端、QA|已评审基线|任务拆分、依赖图、接口样例、开发环境说明、完成定义|每个任务有验收条件及负责人|
|规则与数据开发|规则引擎工程师、数值／数据工程师|规则决策表、数据字典|引擎、导入数据、单元测试、数据校验报告|金额、轮序、胜负及异常结算正确|
|纵向切片|前端、后端、UI／动效、QA|接口契约、页面规格、引擎|可玩单回合版本、联调记录、问题单|从开局到一次买卖、存档恢复贯通|
|全功能迭代|前后端、规则、美术音频、QA|任务与基线|功能版本、变更记录、代码评审、接口更新、回归报告|关键功能覆盖，差异明确|
|稳定与候选发布|QA、技术负责人、运维|完整构建及缺陷台账|兼容／断网／联机／性能／视觉报告、候选包、校验值、回退说明|阻断缺陷关闭，构建可重复验证|
|验收与发布|产品负责人、规则审阅者、QA、实际用户、发布负责人|候选包、需求追踪表、已知问题|UAT记录、验收结论、问题豁免、发布记录|对约定范围明确通过或不通过|
|维护|产品、研发、QA、运维|用户反馈、运行数据|缺陷单、修复说明、影响分析、回归报告、版本归档|修复可追溯且没有破坏旧功能|

可选岗位：多人规模扩大后增加专职后端／实时网络工程师、SRE、安全工程师；需要专门动效和声音时增加技术美术、音频设计师；涉及第三方作品和素材时安排授权资料审查职责。岗位数量取决于规模，不需要每项职责都单独招聘。

开发子阶段依次为：环境和骨架 → 规则引擎与数据 → 可玩的纵向切片 → 单机完整循环 → 联机与恢复 → 内容和表现补齐 → 缺陷收敛 → 发布候选。规则、UI与网络可以并行，但依赖同一份状态与指令契约。
